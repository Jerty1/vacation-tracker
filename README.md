# Учёт отпусков — Vacation Tracker

REST API для небольшой компании: сотрудники, заявки на отпуск, согласование и
годовой баланс. Взаимодействие происходит через Django REST Framework.

## Возможности и правила

- Добавление сотрудников: ФИО и должность.
- Создание заявки: сотрудник, начало и окончание; начальный статус `pending`.
- Согласование и отклонение только из статуса `pending`.
- Баланс за указанный год: `total`, `used`, `remaining`.
- Каждому сотруднику положено **28 календарных дней в год**; обе граничные даты,
  выходные и праздники включаются. Например, 1–7 февраля — 7 дней.
- `pending` и `approved` занимают баланс; `rejected` и `cancelled` не занимают.
- Дата окончания не раньше начала; начало не в прошлом; весь отпуск в одном
  календарном году; длительность не больше остатка.
- Начать отпуск сегодня разрешено. «Сегодня» определяется часовым поясом
  `Europe/Moscow`, который можно изменить через `DJANGO_TIME_ZONE`.
- Остаток считается отдельно по каждому сотруднику и году, без переноса дней.
- Действующие заявки одного сотрудника не пересекаются, включая совпадение
  граничных дат. Заявки разных сотрудников могут пересекаться.
- Отмена `pending` или `approved` разрешена **строго до даты начала**. Дни
  возвращаются на баланс. В день начала и позднее отмена запрещена.
- История создания и изменения статусов содержит время и `changed_by`.
- Swagger/OpenAPI, админка, тесты, линтер и GitHub Actions.

### Статусы

| Значение API | Отображаемый статус | Занимает баланс | Допустимые действия |
| --- | --- | --- | --- |
| `pending` | На согласовании | Да | Согласовать, отклонить, отменить до начала |
| `approved` | Согласовано | Да | Отменить до начала |
| `rejected` | Отклонено | Нет | Нет |
| `cancelled` | Отменено | Нет | Нет |

`cancelled` — дополнительный статус для бонусного сценария отмены. Три обязательных
статуса сохранены. Одобренную заявку нельзя отклонить или согласовать повторно.
Отменённую/отклонённую заявку нельзя вернуть на согласование; нужна новая заявка.

## Стек

- Python **3.10+**, Django **5.2**, Django REST Framework **3.16**.
- SQLite по умолчанию; настройки PostgreSQL и драйвер psycopg включены.
- drf-spectacular для OpenAPI, Ruff для линтинга/форматирования, coverage.py.
- Версии прямых зависимостей закреплены в `requirements*.txt`.

## Быстрый запуск: SQLite

Распакуйте проект и откройте терминал в каталоге с `manage.py`.

### Linux / macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python manage.py migrate
python manage.py runserver
```

### Windows PowerShell

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python manage.py migrate
python manage.py runserver
```

Если выполнение `Activate.ps1` запрещено настройками PowerShell, используйте
`.\.venv\Scripts\python.exe` вместо `python` в командах без активации окружения.

Откройте:

- [Swagger UI](http://127.0.0.1:8000/api/docs/).
- [OpenAPI](http://127.0.0.1:8000/api/schema/).
- [Корень API](http://127.0.0.1:8000/api/).
- [Django admin](http://127.0.0.1:8000/admin/).

Для админки создайте пользователя отдельной командой:

```bash
python manage.py createsuperuser
```

Сотрудников можно добавлять/редактировать через админку. Заявки и историю можно
просматривать и фильтровать; их изменение в админке отключено, чтобы не обходить
правила API и запись истории.

После `migrate` создаётся файл `db.sqlite3`. Остановка и повторный запуск сервера
его не удаляют. База и локальные секреты исключены из Git.

## Переменные окружения

Для запуска с SQLite переменные задавать не нужно. `.env.example` перечисляет
доступные настройки. **Файл `.env` не загружается автоматически**: используйте
переменные терминала или своего менеджера процессов.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DJANGO_DEBUG` | `true` | Режим локальной разработки |
| `DJANGO_SECRET_KEY` | Генерируется в памяти при DEBUG | Обязателен при `DJANGO_DEBUG=false` |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1,[::1]` | Разрешённые хосты через запятую |
| `DJANGO_TIME_ZONE` | `Europe/Moscow` | Часовой пояс проверки дат |
| `DB_ENGINE` | `sqlite` | `sqlite` или `postgresql` |
| `SQLITE_PATH` | `db.sqlite3` в корне | Путь к SQLite-файлу |
| `POSTGRES_DB` | `vacations` | Имя БД PostgreSQL |
| `POSTGRES_USER` | `vacations` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Пусто | Пароль из вашего окружения |
| `POSTGRES_HOST` | `localhost` | Хост PostgreSQL |
| `POSTGRES_PORT` | `5432` | Порт PostgreSQL |

Ключ Django в локальном режиме генерируется при старте и не сохраняется в коде.
Из-за смены ключа сессия админки после перезапуска может потребовать повторного
входа. Для постоянной сессии задайте собственный `DJANGO_SECRET_KEY`.

### PostgreSQL вместо SQLite

Создайте пустую БД и пользователя с доступом к ней в своём PostgreSQL. Затем,
например, в Linux/macOS:

```bash
export DB_ENGINE=postgresql
export POSTGRES_DB=vacations
export POSTGRES_USER=vacations
export POSTGRES_HOST=localhost
export POSTGRES_PORT=5432
read -rsp 'PostgreSQL password: ' POSTGRES_PASSWORD
export POSTGRES_PASSWORD
python manage.py migrate
python manage.py runserver
```

В PowerShell переменные задаются через `$env:ИМЯ = 'значение'`. Пароли и ключи
нельзя добавлять в репозиторий. Для тестов на PostgreSQL пользователю БД требуется
право создавать тестовую базу.

По заданию API работает **без авторизации и разграничения прав**. В `changed_by`
передаётся имя автора со слов клиента; при отсутствии — `anonymous`. Это журнал
действий, а не подтверждённая идентификация. Django admin использует штатный вход.
Сервер разработки предназначен для локальной проверки задания.

## Эндпойнты

Все URL заканчиваются `/`; JSON передаётся с `Content-Type: application/json`.
Даты имеют формат `YYYY-MM-DD`. Параметр `year` — целое число от 1 до 9999.

| Метод | URL | Назначение |
| --- | --- | --- |
| GET | `/api/employees/` | Список сотрудников |
| POST | `/api/employees/` | Добавить сотрудника |
| GET | `/api/employees/{id}/` | Сотрудник по ID |
| GET | `/api/employees/{id}/balance/?year=2027` | Годовой баланс |
| GET | `/api/vacations/` | Список заявок |
| POST | `/api/vacations/` | Подать заявку |
| GET | `/api/vacations/{id}/` | Заявка по ID |
| POST | `/api/vacations/{id}/approve/` | Согласовать |
| POST | `/api/vacations/{id}/reject/` | Отклонить |
| POST | `/api/vacations/{id}/cancel/` | Отменить до начала |
| GET | `/api/vacations/{id}/history/` | История заявки |
| GET | `/api/schema/` | OpenAPI-схема |
| GET | `/api/docs/` | Swagger UI |

Редактирование и удаление сотрудников/заявок через API не предусмотрены;
`PUT`, `PATCH`, `DELETE` возвращают `405`. Статус меняется только отдельными
действиями. Неизвестные и недоступные для записи поля возвращают `400`, включая
попытку передать `status` при создании заявки.

### 1. Добавить сотрудника

Примеры ниже рассчитаны на пустую базу: сотрудник и заявка получат ID `1`.
Если база уже заполнена, возьмите ID из фактического ответа.

```bash
curl -X POST http://127.0.0.1:8000/api/employees/ \
  -H 'Content-Type: application/json' \
  -d '{"full_name":"Иванов Иван Иванович","position":"Аналитик"}'
```

Ответ `201 Created`:

```json
{
  "id": 1,
  "full_name": "Иванов Иван Иванович",
  "position": "Аналитик",
  "created_at": "2026-11-20T12:00:00+03:00"
}
```

### 2. Подать заявку

Пример использует 2027 год. Если запускаете проект позже, замените даты на
будущие в одном году и тот же год используйте в запросе баланса.

```bash
curl -X POST http://127.0.0.1:8000/api/vacations/ \
  -H 'Content-Type: application/json' \
  -d '{"employee":1,"start_date":"2027-02-01","end_date":"2027-02-07","changed_by":"Иванов И.И."}'
```

Ответ `201 Created`:

```json
{
  "id": 1,
  "employee": 1,
  "start_date": "2027-02-01",
  "end_date": "2027-02-07",
  "days": 7,
  "status": "pending",
  "status_display": "На согласовании",
  "created_at": "2026-11-20T12:01:00+03:00",
  "updated_at": "2026-11-20T12:01:00+03:00"
}
```

### 3. Согласовать или отклонить

```bash
curl -X POST http://127.0.0.1:8000/api/vacations/1/approve/ \
  -H 'Content-Type: application/json' \
  -d '{"changed_by":"Руководитель"}'
```

Ответ `200 OK`: объект заявки с `status: "approved"` и обновлённым `updated_at`.
Для отклонения **другой заявки на согласовании**:

```bash
curl -X POST http://127.0.0.1:8000/api/vacations/2/reject/ \
  -H 'Content-Type: application/json' \
  -d '{"changed_by":"Руководитель"}'
```

Если заявки `2` нет, ответ будет `404`. Повторное решение по заявке `1` даст `409`.
Допускается тело `{}`: тогда `changed_by` равен `anonymous`.

### 4. Посмотреть баланс и список

```bash
curl 'http://127.0.0.1:8000/api/employees/1/balance/?year=2027'
```

Ответ `200 OK`:

```json
{"employee":1,"year":2027,"total":28,"used":7,"remaining":21}
```

`used` включает и согласованные, и ожидающие решения заявки, даже если даты
отпуска ещё не наступили. Согласование уже зарезервированной заявки не списывает
дни повторно.

```bash
curl 'http://127.0.0.1:8000/api/vacations/?employee=1&year=2027&status=approved'
curl 'http://127.0.0.1:8000/api/employees/?page=1'
curl 'http://127.0.0.1:8000/api/vacations/1/'
```

Фильтры списка заявок: `employee`, `year`, `status`; их можно комбинировать.
Некорректное значение/неизвестный фильтр возвращает `400`. Несуществующий ID
сотрудника в фильтре даёт пустой список. Списки сотрудников/заявок разбиты на
страницы по 50 записей; используется параметр `page`.

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [{"id": 1, "employee": 1, "status": "approved"}]
}
```

В примере списка объект заявки сокращён; фактический объект содержит все поля
из ответа создания. Порядок заявок — сначала новые, сотрудников — по ID.

### 5. Отменить заявку и посмотреть историю

```bash
curl -X POST http://127.0.0.1:8000/api/vacations/1/cancel/ \
  -H 'Content-Type: application/json' \
  -d '{"changed_by":"Иванов И.И."}'
curl 'http://127.0.0.1:8000/api/vacations/1/history/'
curl 'http://127.0.0.1:8000/api/employees/1/balance/?year=2027'
```

Отмена возвращает объект заявки со статусом `cancelled`; баланс снова равен
`total=28`, `used=0`, `remaining=28`. История — массив событий по времени от
старых к новым, без пагинации:

```json
[
  {"id":1,"from_status":"","to_status":"pending","changed_by":"Иванов И.И.","changed_at":"2026-11-20T12:01:00+03:00"},
  {"id":2,"from_status":"pending","to_status":"approved","changed_by":"Руководитель","changed_at":"2026-11-20T12:02:00+03:00"},
  {"id":3,"from_status":"approved","to_status":"cancelled","changed_by":"Иванов И.И.","changed_at":"2026-11-20T12:03:00+03:00"}
]
```

Пустой `from_status` обозначает создание заявки. Неуспешные изменения не
создают событий истории.

### Ошибки

| HTTP | Причина | Пример тела |
| --- | --- | --- |
| 400 | Даты, баланс, пересечение или поля запроса невалидны | `{"end_date":["Отпуск должен быть в рамках одного года."]}` |
| 400 | На балансе недостаточно дней | `{"days":["Недостаточно дней: доступно 0, нужно 1."]}` |
| 404 | Сотрудник, заявка или страница не найдены | `{"detail":"..."}` |
| 405 | Метод не поддерживается | `{"detail":"..."}` |
| 409 | Повторное решение, недопустимый переход или поздняя отмена | `{"detail":"..."}` |
| 503 | SQLite остаётся заблокированной после ожидания | `{"detail":"База данных занята. Повторите запрос."}` |

Для `503` возвращается заголовок `Retry-After: 1`. Проверка правил выполняется
до сохранения заявки; баланс и история при ошибке не изменяются.

HTTP-сценарий с перезапуском сервера прошли. Совместимость зависимостей с Python
3.10 дополнительно проверена разрешением пакетов; реальный прогон на Python

```bash
ruff check .

python manage.py check
python manage.py makemigrations --check --dry-run
coverage run manage.py test --noinput
coverage report
python manage.py spectacular --validate --fail-on-warn --file schema.yaml

```

Тесты проверяют обязательный сценарий, неверные/прошедшие даты, разные годы,

пересечения, матрицу переходов, отмену, историю, атомарность, ошибки API и админку.
Отдельные тесты отправляют параллельные HTTP-запросы через DRF test client:
сверхбаланс, пересечение и два конкурирующих решения.

`smoke_test.py` запускает настоящий сервер, выполняет основной сценарий через
HTTP, останавливает и заново запускает сервер с той же БД, затем проверяет
сохранность сотрудника, заявки и баланса. Использует отдельную временную SQLite
базу и будущие даты; вашу рабочую БД не изменяет.

Для SQLite тесты используют отдельный файл `test.sqlite3` в корне проекта;
никогда не храните в нём рабочие данные. Этот файл создаётся и удаляется тестовым
раннером. GitHub Actions настроен на Python 3.10/3.12/3.13 с SQLite и отдельный
прогон на PostgreSQL 17 после публикации репозитория.

## Структура и защита от одновременных изменений

```text
config/                  настройки, маршруты, WSGI/ASGI
vacations/models.py      сотрудник, заявка, история
vacations/services.py    правила, баланс и атомарные изменения
vacations/serializers.py проверка входных полей и формат JSON
vacations/views.py       REST-эндпойнты
vacations/admin.py       админка
vacations/migrations/    миграции схемы БД
vacations/tests/         функциональные и конкурентные тесты
scripts/smoke_test.py    HTTP-сценарий с перезапуском сервера
.github/workflows/       автоматические проверки
```

Длительность вычисляется из дат, баланс — из действующих заявок: отдельный
счётчик дней не хранится и не может рассинхронизироваться.

Создание и изменение статуса выполняются в `transaction.atomic`. В PostgreSQL
сначала блокируется строка сотрудника через `select_for_update`, затем заявка.
Все действия используют один порядок блокировок. В SQLite установлен режим
транзакций `IMMEDIATE`: блокировка записи берётся до чтения баланса. Поэтому две
заявки одновременно не могут обе потратить один и тот же остаток или пройти
проверку пересечения. SQLite допускает только одного писателя; время ожидания
блокировки — 20 секунд. Для высокой нагрузки подходит PostgreSQL.

История сохраняется в той же транзакции, что и заявка. В БД дополнительно
проверяются порядок дат, один год и допустимые значения статуса. Правила суммы
дней, текущей даты и переходов реализованы сервисным слоем. Прямое изменение
базы/ORM в обход сервиса не является публичным интерфейсом приложения.

Удаление сотрудника с заявками и заявки с историей защищено внешними ключами
`PROTECT`. Секреты не включены в проект; `.env`, базы данных, окружения и кэши
исключены через `.gitignore`.

## Публикация и сдача на GitHub

Если проект получен как архив, после распаковки выполните команды из корня.
Нужны Git, GitHub CLI (`gh`) и вход в **ваш** GitHub-аккаунт.

```bash
git init -b main
git add .
git commit -m "Implement vacation tracking REST API"
gh auth login
gh repo create vacation-tracker --public --source=. --remote=origin --push
gh repo view --json url,visibility
```

Если Git не знает ваше имя/email, задайте их через локальные `git config
user.name` и `git config user.email` перед коммитом. Если репозиторий с этим
именем существует, выберите другое имя в `gh repo create`.

В ответе `gh repo view` проверьте `visibility: "PUBLIC"`; ссылку из `url`
отправьте проверяющему. Перейдите во вкладку Actions и дождитесь завершения
проверок. Сам архив не создаёт репозиторий GitHub: публикация требует доступа к
аккаунту владельца.
